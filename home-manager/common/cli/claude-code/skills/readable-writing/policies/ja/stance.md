# 立場

書き手が何を引き受けているかに出る言い回しを扱う。

## 検出対象

### 反証できない主張

- `本質的な問題がある`
- `構造的な課題である`
- `示唆に富む結果だ`
- `重大な意味を持つ`
- `根本的な転換が必要だ`
- `深い洞察が得られる`
- `重要な示唆を含む`
- `○○することが大切です`
- `○○に他なりません`

#### AI版

```
このリファクタリングには本質的な問題がある。構造的な課題であり、根本的な転換が必要だ。
```

#### 修正版

```
このリファクタリングでは、`OrderService` が `PaymentGateway` を直接呼んでいる箇所が7つ残った。
```

### 結論の回避

- `ケースバイケース`
- `場合によります`
- `価値観によります`
- `状況に応じて異なります`
- `一概には言えませんが`
- `一般的には`
- `メリットもあればデメリットもあります`
- `○○という側面もありますが、一方で〜`
- `賛否が分かれるテーマです`

#### AI版

```
モノレポにするかどうかはケースバイケースです。メリットもあればデメリットもあり、一概には言えません。
```

#### 修正版

```
モノレポにした。パッケージが3つしかなく、バージョンを揃える手間のほうが大きかった。
```

### 全方位肯定

| AI版 | 修正版 |
|---|---|
| それぞれに独自の強みがあり、用途による | これを使っている。あれはやめた |
| 賛否が分かれるテーマです | この構成にした |
| メリットもデメリットもあります | これはいい。これは駄目だった |

#### AI版

```
Notion、Obsidian、Logseqそれぞれに独自の強みがあり、用途やワークフローによって最適な選択は異なります。Notionはチーム共有に優れ、Obsidianはローカル管理とリンク機能が強力で、Logseqはアウトライナーとしての完成度が高いと言えるでしょう。
```

#### 修正版

```
Obsidianを採用した。ローカルで動き、リンクの解決が速い。Notionは同期が重くて外した。Logseqはアウトライナーとしては良いが、Markdownを直接編集する運用と噛み合わなかった。
```

採用したものを主語に立て、選ばなかったものにも理由を付ける。

### 弱い否定

- `あまり推奨されません`
- `注意が必要です`
- `望ましくないとされています`
- `避けたほうが良いでしょう`

| AI版 | 修正版 |
|---|---|
| ファイル数が増えると遅くなる可能性があるため、注意が必要です | ファイルが1000を超えると、この方式は1回1分以上かかる |

### 強度の振り切り

- `劇的に改善`
- `圧倒的に速い`
- `大幅に削減`
- `飛躍的に向上`
- `爆速`
- `絶対に避けるべき`
- `論外`

#### AI版

```
インデックスを張ったらクエリが劇的に改善した。爆速になったと言っていい。
```

#### 修正版

```
インデックスを張ったら、このクエリが平均1200msから40msになった。
```

### 根拠のない強い評価

- `非常に有効です`
- `画期的な手法です`
- `革新的なアプローチです`
- `大きなメリットがあります`
- `驚くべき効果が期待できます`

#### AI版

```
この手法は非常に有効です。画期的なアプローチで、大きなメリットがあります。
```

#### 修正版

```
この手法で、レビュー待ちの平均が2日から半日になった。3ヶ月分のPR120本で測った。
```

### ヘッジの重ね掛け

- `○○ことがある`
- `○○場合がある`
- `○○可能性がある`
- `○○なりうる`
- `○○とは限らない`
- `○○と言えなくもない`
- `あくまで○○として捉えるのが正確だ`

| AI版 | 修正版 |
|---|---|
| あくまで個人の経験に基づく見解であり、組織の規模によって結果は異なる可能性がある | 10人規模のウチのチームでの話 |

### 儀式化した免責

| AI版 | 修正版 |
|---|---|
| あくまで個人の経験に基づく見解であり、定量的な検証ではない | 書かない |
| 環境やケースによって結果は異なる可能性がある | 書かない。または「ウチではこうだった」とだけ |
| 実装はモデルによって異なる | 書かない |

#### AI版

```
私のチームではこの方法でリリース頻度が上がった。ただし、これはあくまで個人の経験に基づく見解であり、定量的に検証したものではない。組織の規模や文化によって結果は異なる可能性があるため、参考程度に捉えていただきたい。
```

#### 修正版

```
10人規模のウチのチームでは、この方法でリリース頻度が週1から週3に上がった。
```

保険を具体的な適用範囲として1回だけ書き、主張は打ち消さずに残す。
