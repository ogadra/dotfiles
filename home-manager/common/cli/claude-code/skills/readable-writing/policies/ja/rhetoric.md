# 修辞

パターンと直し方は `common/rhetoric.md` にある。ここには日本語の言い回しと例を置く。

## 検出対象

### 二項対比

| AI版 | 修正 |
|---|---|
| 「Aではなく、Bである」 | 「Bだ」と直接書く |
| 「単なるAではなく、Bだ」 | 「Bだ」 |
| 「Aだけじゃなく、Bでもある」 | 「Bだ」 |
| 「実はAではなくBだった」 | 「Bだった」 |
| 「Aに見えるが、Bだ」 | 「Bだ」 |
| 「Aではなくなり、Bになる」 | 「Bになった」 |
| 「重要なのはAではなくBだ」 | 「Bが効いている」 |

#### AI版

```
これは単なる効率化ツールではない。これは思考のパートナーだ。
AIは置き換えるためのものではなく、拡張するためのものだ。
重要なのは速度ではなく、深さである。
```

#### 修正版

```
AIに下書きを書かせると、自分の考えを言語化しやすくなる。作業を置き換えるというより、検討の幅が広がる。書く速さより、検討の抜けが減るほうが効いている。
```

### 否定的列挙

| AI版 | 修正 |
|---|---|
| 「Aではない。Bでもない。Cだ。」 | 「Cだ」 |
| 「これは戦略ではなく、戦術でもなく、習慣だ」 | 「これは習慣だ」 |
| 「彼は研究者でも、エンジニアでもなく、職人だった」 | 「彼は職人だった」 |

### 劇的な断片化

体言止めと句点で間を作ろうとする形。

| AI版 | 修正 |
|---|---|
| 「シンプル。それだけ。それが本質。」 | 「シンプルだ」 |
| 「速く。正確に。継続的に。」 | 「速く正確に続ける」 |
| 「これがすべてを変える。本当に。すべてを。」 | 「これで状況が変わる」 |

#### AI版

```
これは小手先のテクニックではない。一時的な流行でもない。働き方そのものの変化だ。
速く。深く。そして静かに。それが、これからのスタンダードになる。
```

#### 修正版

```
これは開発の進め方そのものが変わる話だと思う。気づいたら当たり前になっているタイプの変化だろう。
```

否定的列挙をやめて「進め方が変わる」を直接書いた。断片化した体言止めも普通の文に戻している。

### 修辞疑問

- `なぜか。`
- `どういうことか。`
- `本当にそうだろうか。`

#### AI版

```
Claudeで書いたドキュメントが、レビューで「読みにくい」と返ってきた。なぜか。どういうことか。
```

#### 修正版

```
Claudeで書いたドキュメントが、レビューで「読みにくい」と返ってきたので、指摘の内容を集計した。
```

#### 修正の型

「なぜか」は「集計した」のような、次にやったことに置き換える。

#### AI版

```
ChatGPTを使えば誰でも記事が書ける。そう信じて活用してきたライターは多いはずだ。しかし──
```

#### 修正版

```
最近、ChatGPTで記事書くより、自分で下書きしたほうが結局早いんじゃないか、と思うようになってきた。きっかけは、
```

#### 技術文書のAI版

```
Claudeを使えば誰でも質の高いドキュメントが書ける──そう信じて導入したチームは多いはずだ。しかし、いざレビューに出すと「読みにくい」と返ってくる。なぜか。
```

#### 技術文書の修正版

```
Claudeで設計ドキュメントを書くようになって半年経つが、レビューで「読みにくい」と指摘されることが増えた。どこが読みにくいのか言語化できていなかったので、指摘の内容を集計した。
```

決めつけを実際に起きたことに変え、「なぜか」の煽りを「集計した」に置き換えると、次の節への動機付けになる。

### 定型の語り出し

- `気づいたときには、すでに○○だった`
- `あの日、私は○○していた`

#### AI版

```
気づいたときには、すでにビルドは9分かかっていた。あの日、私はCIのログをただ眺めていた。
```

#### 修正版

```
9月にCIのログを見て、初回ビルドに9分かかっていることに気づいた。
```

#### 修正の型

その日に実際にやったことから書き出す。

### 一文圧縮

#### AI版

```
JavaScriptは1995年にBrendan Eichが10日間で設計した。この言語は瞬く間に普及した──しかし型安全性は設計目標に含まれていなかった。
```

#### 修正版

```
JavaScriptは、もともと1995年にBrendan Eichが作った言語だ。10日ほどで設計されたらしい。そこから急速に普及し、今のWebの標準になった。ただ、Brendan Eichは開発当時、型安全性をあまり考えていなかったようだ。それがTypeScriptが生まれた背景になっている。
```

- 調べただけの事実に入れる伝聞表現
    - らしい
    - ようだ
    - と聞いた

### ムラの欠如

#### AI版

```
第一に、責任の所在を明確にすることが重要です。これにより、問題発生時の対応速度が上がります。

第二に、定期的なレビューを実施することが必要です。これにより、品質を継続的に改善できます。

第三に、ナレッジ共有の仕組みを作ることが効果的です。これにより、組織全体の学習速度が向上します。
```

#### 修正版

```
一番大事なのは、誰がやるか決めること。決めておかないと、問題が起きたときに全員が様子見になる。

あとは月1でレビュー会を入れる。やらないとチームの認識がずれる。

ナレッジ共有は難しい。Notionを整備するとか色々やったが、書きたい人が書きたいときに書く以上のものはなかなか機能しない。
```

段落の長さをバラけさせ、「第一に」「第二に」「第三に」の並列を崩した。最後の段落は結論を保留したままにしてある。

### 段落の均一な閉じ方

- 感想で閉じる形
    - `〜なんだなと感じました`
    - `〜ということが分かりました`
    - `〜の重要性を痛感しました`
- 効能で閉じる形
    - `これにより〜が向上します`

#### AI版

```
キャッシュを挟んだら9分のビルドが3分になった。効果の大きさを痛感しました。

CIのコストも下がった。これにより運用費が改善します。

待ち時間も減った。集中が続くということが分かりました。
```

#### 修正版

```
キャッシュを挟んだら9分のビルドが3分になった。

CIのコストも下がったはずだ。請求書はまだ見ていない。

一番効いたのは待ち時間で、ブランチを切り替えて別の作業を始めることがなくなった。
```

#### 修正の型

感想と効能の閉じ方を消す。段落ごとに終わり方の形を変える。

### 文頭のクセ

- `実は、` で始まる文
    - 削除する
- `そして、` `また、` の連続
    - 崩す

#### AI版

```
実は、キャッシュのキー設計が効いていた。そして、`package-lock.json` のハッシュを使うようにした。また、`.next/cache` も対象に含めた。そして、ビルドが3分になった。
```

#### 修正版

```
キャッシュのキー設計が効いていた。`package-lock.json` のハッシュを使い、`.next/cache` も対象に含めたら、ビルドが3分になった。
```
