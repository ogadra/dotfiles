## 見出しの代用

節の区切りを太字とコロンで作る形。行頭に単独で置く太字や、コロンで終わる裸の行を見出しの位置に置く。Markdownとしてはただの装飾なので、アンカーも目次も階層も付かない。折りたたみやアウトライン表示も効かない。

### AI版

```
**AI版:**

> 本文

検出したパターン:
- 冗長な前置き

**Before:**

> body

What's wrong:
- Redundant preamble
```

### 修正版

```
### AI版

> 本文

### 検出したパターン

- 冗長な前置き

### Before

> body

### What's wrong

- Redundant preamble
```

### 修正の型

行頭に単独で置く太字と、コロンで終わる裸の行を見つけたら、3つのどれかにする。

- 節の区切りの場合
    - 見出しにする
- 直前の文の一部の場合
    - その文に畳む
- どちらでもない場合
    - 消す

## 命題型の見出し

見出しに主張を置く形。見出しはテーマの名前、つまり名詞句で立てる。英語の `How X solves Y` 構造の輸入。

命題型の見出しを立てると、本文にはその主張の裏付けを並べることになる。読み手が探している情報ではなく、書き手の結論の補強が節ごとに並ぶ。

さらに悪化した形として、見出しで主張を置き、本文冒頭で同じ主張を言い換えて繰り返すものがある。

### 修正の型

見出しを名詞句にして、本文は具体例から入る。

## 見出しと中身のずれ

見出しを立てたあと、手元にある材料でそこを埋める形。依頼された作業内容しか持っていないので、「目的」の下に手段を並べてしまう。読み手はなぜやるのかを探して見つけられない。

ずれは他の見出しでも起きる。

- 「背景」の下に仕様を並べる
- 「課題」の下に解決策を並べる
- 「概要」の下に詳細を並べる
- "Background" が仕様の一覧になる
- "Problem" が解決策の一覧になる
- "Overview" が詳細の一覧になる

### 修正の型

見出しが約束したものを本文に置く。書けないなら、見出しのほうを中身に合わせて変える。

## 対象外の列挙

何かを定義するとき、まず「これは何ではないか」を並べる形。文書のレベルでは「対象外」「スコープ外」「Non-goals」「本ドキュメントでは扱わない」の節になる。読み手がまだ聞いていないことに先回りして答えている。

### AI版

```
## 対象
- 技術文書
- README

## 対象外
- 体験記
- 感想

## In scope
- Technical docs
- READMEs

## Out of scope
- Trip reports
- Opinion pieces
```

### 修正版

```
## 対象
- 技術文書
- README

## In scope
- Technical docs
- READMEs
```

### 修正の型

対象を書けば、書かれていないものは対象外だと読み手が判断できる。文のレベルの「AではなくBだ」は `common/rhetoric.md` の二項対比を参照。

## 経緯の記録

文書を直したとき、直した跡を文書に残す形。「変更点」の節を作り、何を足して何を消したかを並べる。読み手が知りたいのは今どうなっているかで、変更の記録はコミットとPRを見れば分かる。

### AI版

```
## 変更点

- 2つのスキルを1つに統合した
- 常体で書くルールを足した

## Changes

- Merged the two skills into one
- Added the plain-form rule
```

### 修正の型

「以前は」「元は」「〜に変更した」も残さない。最初からその形だった文書として書く。派生元のライセンスと出典は、今その文書が何であるかの一部なので残す。

## 例外条項の後付け

ルールを書いたあと、そのルールに合わない事例に気づいて「ただし〜の場合は」を足す形。ルール本体を直さないまま逃げ道だけを足すので、どこまでが原則でどこからが例外なのか分からなくなる。

### AI版

```
文末は「だ」「である」で統一する。
ただし箇条書きや仕様の列挙では体言止めでよい。

Write every sentence in the active voice.
That said, passive is fine when the actor is unknown or irrelevant.
```

### 修正版

```
常体で書く。「です」「ます」は使わない。

Name the actor in every sentence.
```

### 修正の型

例外が要ると気づいたときは、ルール本体を書き直す。書き直せば例外は消える。

## メタ的な構造宣言

本文の中で構造を予告する形。見出しで分かることを本文で再宣言しない。

### 修正の型

見出しで「RAGの基本」と書き、小見出しで「検索フェーズ」と書けば、構造は明らか。本文での再宣言は要らない。

## 目的の言えない情報

知っている事実を、置ける場所に置く形。書いても害はないという判断で足すので、読み手に何をさせたいのかを決めていない。読む側はそのたびに読み飛ばす判断をさせられ、必要な一文が埋もれる。

### AI版

```
- 依存を入れる
    - `pnpm install`
    - 初回は3分ほどかかる

- Install dependencies
    - `pnpm install`
    - The first run takes about three minutes
```

「初回は3分ほどかかる」で読み手に何をさせたいのかを言えるか確かめる。

- 待つ間に別の作業をしてほしい
    - そう書く
        - 「この間に `.env` を用意しておく」
- 遅いので今後短くしたい
    - 手順書ではなくissueに書く
- どれでもない
    - 消す

### 修正版

```
- 依存を入れる
    - `pnpm install`

- Install dependencies
    - `pnpm install`
```

### 修正の型

目的を言えたとしても、置き場所は別に決める。セットアップ手順は読み手が上から順に実行する文書なので、実行に関係しない情報を挟むと手が止まる。改善の計画は計画の文書に書く。

## 読み手を見ていない補足

誰が読むかを決めないまま補足を足す形。

### AI版

```
`gh run list` と `gh run view` でポーリングしない。完了まで数分かかり、その間ユーザーが指示を出せなくなる。CIの結果はユーザーがGitHub上で見る。

Don't poll with `gh run list` or `gh run view`. It takes minutes, and the user can't give you anything else to do while you wait. They read CI results on GitHub anyway.
```

### 修正版

```
`gh run list` と `gh run view` でポーリングしない。プッシュの成否を報告して作業を終える。

Don't poll with `gh run list` or `gh run view`. Report whether the push succeeded and stop.
```

### 修正の型

補足を書くかどうかは、それを読んで読み手の動作が変わるかで決める。

- 読み手が人の場合
    - 理由を書く
- 読み手がAIの場合
    - 指示が絶対のとき
        - 理由を書かない
    - 判断の余地があるとき
        - 判断の材料になる事実を書く
        - 「テストが3分を超えたら分割を検討する」の3分がこれにあたる

## 検出手順

1. 行頭が `**` で始まり、その行に他の文が無い行を検索する。
2. コロンで終わる裸の行を検索する。
3. 見出しをすべて抜き出し、名詞句になっていないものを集める。
4. 見出しごとに、直下の本文がその見出しの語に答えているか確かめる
    - 優先して見る見出し
        - 「目的」
        - 「背景」
        - 「課題」
        - 「概要」
5. 対象外の列挙を検索する
    - 「対象外」
    - 「スコープ外」
    - 「Non-goals」
    - 「扱わない」
6. 経緯の記録を検索する
    - 「変更点」
    - 「以前は」
    - 「元は」
    - 「〜に変更した」
7. 例外条項を検索する
    - 「ただし」
    - 「なお、〜の場合は」
    - 直前がルールの記述か確かめる
8. 各節の冒頭段落を集め、構造の予告になっていないか確かめる。
9. 手順書と設定の説明で、実行に関係しない一文が挟まっていないか確かめる。
